# Break the reference into an editing plan

Start with the viewer's experience. What should they notice, hear and understand? A funny reply may depend on a pause; a boxing punch may depend on contact and its sound. Those are requirements to preserve, not decorative details.

## 1. Watch, listen, then mark the shots

Use the complete local reference, including its ending. Identify cuts, speaking turns, reactions, text changes and sound tails. Write a row for each continuous shot with source in/out, its visual purpose and audio. Do not use a transcript alone to infer expressions or camera movement. If only still frames were inspected, record that limitation.

Keep original media untouched. Put clean reference excerpts in a separate folder. Exclude a platform end card from generation inputs when it is not part of the creative, while retaining the last reaction and spoken tail.

## 2. Give every reference a job

An appearance image controls the person; a performance video shows timing and expression; a voice recording guides speech where the endpoint supports it; a product screenshot defines exact UI. Put those roles in the [reference map](../skills/video-analyzer/templates/reference-map.csv). More files do not automatically produce a better result.

## 3. Choose how to make each layer

| What needs to change? | Practical approach |
|---|---|
| Person, acting or real-world action | Generate a focused performance clip |
| App labels, interface animation or mouse interaction | Build in Remotion |
| New screen inside a moving filmed phone | Track and composite locally; use Blender |
| Captions, diagrams or motion graphics | Author separate editable layers |
| Existing good reply, sound or reaction | Preserve it with its exact source range |
| Only loudness differs between adjacent clips | Adjust gain and listen to the join |

The [language-app example](../examples/language-app.md) and [boxing example](../examples/boxing.md) show these decisions in context. Use generation where the performance needs it; fix exact text in the edit.

## 4. Price and approve one batch

Before submitting, show each job's prompt, inputs, model, duration, resolution and audio behavior. Price it with the actual provider quote. Declare whether input video duration is billed, whether native audio changes the charge, and how many retries are allowed. If a price is unverified, label it an estimate. Approval applies to that scope; it should not be requested again for each already approved job.

## 5. Work in parallel, then assemble

Once timings and output sizes are agreed, performance generation, UI construction and graphics can proceed independently. One editor owns the timeline and another person or agent can review it. Follow the [assignment guide](parallel-editing.md) so assets arrive with frame rates, source ranges and audio policies rather than a pile of unnamed MP4 files.

## 6. Check the result as a viewer

Watch the complete raw performance before selecting it. Check exact words, face, gestures, eye direction, unwanted text/music and repeated phrases. Inspect the filmed screen at its hardest motion. Listen to every cut at natural speed. Use gain to match loudness; do not stretch whole sentences merely to fill a clip. Trim picture and its native speech together. Keep voice conversion or replacement narration a separately reviewed choice.

Compare claims with the actual output. A repaired screen is evidence of a local edit; it is not evidence that a model produced exact UI. A successful render only proves a file was made. Save the editable project, selected exports, receipt ledger and review notes so the next change can target the right layer.
